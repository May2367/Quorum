# Quorum Project Progress

Source plan: `plan.txt` in this directory.

## Current Status

The project has been initialized as a Go repository and the first foundation milestone is in place. The work so far is limited to the current `quorum` directory.

Peer transport foundation is now implemented and verified. There is no active background work currently running; the next implementation step is wiring `cmd/quorumd` into a static multi-node cluster and sending `Ready.Messages` through the peer transport.

## Plan Check-In

Checked against `plan.txt` and the current codebase.

### Accomplished and Verified

- Go module, repository layout, generated protobuf/gRPC bindings, and CI workflow exist.
- `internal/raft` has a pure in-memory Raft core with leader election, heartbeats/AppendEntries-style replication, quorum commit advancement, current-term commit guard, and unit tests.
- `internal/storage` has an append-only WAL with CRC records, `fsync`, torn-write recovery, typed Raft hard-state/entry records, and recovery tests.
- `internal/server` has health/readiness endpoints, graceful HTTP shutdown support, a persistent Raft runtime wrapper, committed-log replay into the KV state machine, and initial KV gRPC handlers. `cmd/quorumd` now registers the KV gRPC service for single-node operation.
- `internal/transport` has generated Raft peer protobuf types, Raft message conversion helpers, and a basic gRPC peer client/server foundation.
- `internal/statemachine` has Put, Delete, CAS, revisions, session deduplication, and basic watch event channels with tests.
- Dockerfile, Docker Compose scaffold, Terraform placeholder, chaos/linearizability placeholders, README, and architecture notes exist.
- Latest verification passed with `go test ./...` and `go test -race ./...`.

### Partially Implemented

- Raft persistence exists, but snapshots, InstallSnapshot, and log compaction do not.
- Writes route through a persistent Raft runtime in unit tests and in single-node `quorumd`; peer transport primitives now exist, but `quorumd` does not yet use them for multi-process replication.
- Watches stream new events, but revision-resumable watch history is not implemented.
- Docker Compose exists, but the containers currently run server stubs rather than a functional 3-node cluster.
- Simulated networking has basic drain and partition controls, but not seeded randomized delay/drop/reorder/crash campaigns.

## Direction Update: Settlement Ledger Workload

Decision recorded in this session: Quorum remains a general Raft coordination
service, not a payment system, but the flagship workload will become a
settlement-ledger demo. This preserves the distributed-systems focus while
making leases, fencing tokens, watches, and exactly-once execution concrete.

Plan impact:

- Phase 3 stale fencing-token testing will use the ledger itself as the guarded
  resource instead of a separate fake storage resource.
- Phase 4 job scheduler becomes a settlement/payout worker system. Jobs move
  integer cents from escrow accounts to merchant accounts.
- The ledger API is deliberately small: `CreateAccount`, `Transfer`, and
  `GetBalance`.
- `Transfer` will be a replicated state-machine command so two-account updates
  are atomic under Raft.
- Settlement jobs will use the job ID as the idempotency key.
- Final verification should check every job exactly once, total money conserved,
  no negative balances, no stale-worker writes accepted, and no committed
  transfers lost across leader failover.
- The standalone seat-booking stress test is no longer core scope. Its
  concurrency target can be folded into the settlement-ledger workload.
- Payment-processor features remain explicitly out of scope: reserve/capture,
  voids, transaction listing, double-entry accounting, auth, merchants,
  webhooks, refunds, and external payment integrations.

Implementation direction:

- The next server milestone should use an asynchronous Raft driver rather than
  the earlier minimal synchronous peer-message loop.
- The async driver should own the persistent Raft runtime behind an event loop,
  accept ticks/peer messages/proposals over channels, persist each `Ready`, send
  outbound messages through per-peer workers, apply committed entries in order,
  and complete client proposals once their commands are applied.

Status of this update:

- `plan.txt` now has an appended amendment describing the settlement-ledger
  workload, async driver direction, phase impacts, out-of-scope boundaries, and
  optional extras.
- No code has been changed for this direction yet.
